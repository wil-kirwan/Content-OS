Product Requirements Document
Product name

Working name: Content OS for HighLevel

Product vision

Build a modular planning and execution platform for businesses that grow through short-form and long-form content.

The product starts with a master marketing planner that acts as the operating system for monthly marketing execution. Over time, new modules plug into the same workspace, data model, and HighLevel connection layer.

Why this product should exist

Right now, most growing businesses have content ideas, partial plans, scattered assets, and disconnected execution. Their blog plan lives in one place, social ideas in another, email campaigns somewhere else, and HighLevel execution happens after the fact.

Your spreadsheet already points to the real need. This is not just a content calendar. It is a cross-channel marketing command center.

The first module should let a business:

plan every major marketing motion in one place
see what is scheduled by day, week, and month
connect planning to real execution inside HighLevel
pull activity back from HighLevel so the planner becomes the source of truth, not a dead document
Users

Primary user:
Business owner, marketing lead, or operator at a content-driven service business.

Secondary users:
Content manager, VA, agency team member, strategist.

Admin user:
Internal team member who configures templates, module defaults, onboarding, and future module rollout.

Product principles
One plan, many channels
The user should not have to manage separate systems for blog, email, social, paid, and site updates.
Plan first, push second
The planner is the operating layer. HighLevel is the execution layer.
Modular from day one
The calendar module is first, but the architecture must support future modules like Audience Alignment, Retention Roadmap, Thumbnail Planning, Idea Ladder, Idea Heist, and Short Form Content Planning.
Low-friction onboarding
The user should be able to connect HighLevel in minutes with a guided flow.
Trustworthy sync
The system must clearly show what came from HighLevel, what was created in the planner, and whether items are synced, draft, published, failed, or out of date.

3. Onboarding and HighLevel connection
Product decision

For MVP, support the manual token flow you requested.

But architect it as an auth provider layer with:

auth type = private_token
auth type = oauth_marketplace

That lets you launch now and move to OAuth later without rewriting the rest of the platform. HighLevel says private integrations are ideal for internal tools and custom systems without building a public app, while OAuth is the right choice for public integrations, Marketplace apps, or broader multi-account access.

Guided HighLevel instructions

HighLevel’s docs say users create a Private Integration in settings, name it, select only the required scopes, and copy the token at creation time because they will not be able to view that same token again later. HighLevel also recommends rotating tokens every 90 days, with a 7-day overlap window during rotation. That means your connector UX needs a “last rotated,” “rotation due,” and “replace token” flow from the start.

How to help users find Location ID

HighLevel documents two simple ways:

Settings → Business Profile
directly from the URL, after /location/ or in the locationId= parameter
Connection health UX

The product should show:

connected
token invalid
token missing scope
location mismatch
sync delayed
reconnect required
Security requirements
encrypt tokens at rest
never display full token after save
display only last 4 characters
test required scopes on connection
support token replacement without deleting workspace data
log all sync and publish actions
4. HighLevel integration strategy
Key architectural call

Do not build this as one giant direct-to-HighLevel calendar.

Build three layers:

Planner layer
Your internal system of record
Connector layer
Auth, scope validation, rate limiting, retry, sync mapping
Adapter layer
Per HighLevel surface, blog, social, email, campaigns, future surfaces
Why

This lets future modules reuse:

auth
workspace
user roles
taxonomy
content themes
campaign objects
reporting
sync jobs
HighLevel API reality

Current HighLevel docs clearly expose:

social planner post endpoints including get, create, edit, and delete
blog endpoints including create, update, list blogs, and list blog posts by blog
email campaign retrieval endpoints, plus campaign statistics and draft update endpoints
webhooks and real-time event delivery for many platform events
Important product constraint

I found strong support for creating social posts and blog posts in the current docs I reviewed. For email, I found list, stats, and draft update coverage, but I did not find a clearly surfaced create-email-campaign endpoint in that same pass. So for V1, I would treat email as:

read and sync first
deep-link into HighLevel for campaign creation if needed
expand to draft creation only after confirming the exact write path in implementation
Recommended sync model by surface
Surface	Pull from HighLevel	Push to HighLevel	V1 Decision
Social Planner	Yes	Yes	Full V1 support
Blogs	Yes	Yes	Full V1 support
Email campaigns	Yes	Partial, cautious	Sync first, controlled write later
SMS planning	Planner-first	Later	V1 planning only
Website elements	Planner-first	Later	V1 planning only
Influencers	No native dependency	No	Planner-only
Affiliates	No native dependency	No	Planner-only
Rate limiting requirement

HighLevel currently documents rate limits of 100 requests per 10 seconds per resource and 200,000 requests per day per resource. So sync must be queued, incremental, and retry-safe, not chatty.

Eventing requirement

Use webhooks where HighLevel supports the event you need, and polling only where webhook coverage is missing. HighLevel’s docs position webhooks as real-time notifications and expose a webhook logs dashboard for debugging delivery.

10. Future module architecture

This is where most products fail. They solve calendar first, then discover later modules do not fit.

You should define a module contract now.

Each future module should have:

module metadata
custom entities
shared taxonomy access
shared campaign access
planner item references, if relevant
optional HighLevel sync adapter
optional analytics adapter
Example

Audience Alignment should not be a separate random tool.

It should define:

audience segments
pains
desires
offers
objections
brand voice
channel notes

Then those values become available in:

planner templates
item briefs
campaign setup
future AI-assisted generation

That same pattern applies to:

Retention Roadmap
Thumbnail Planning
Idea Ladder
Idea Heist
Short Form Content Planning
Product rule

All modules should be able to write structured insights back into a shared layer, not just store isolated notes.

13. Acceptance criteria for V1

V1 is ready when:

A new user can create an account, connect HighLevel with token plus Location ID, and validate the connection.
A user can load a monthly planner template.
A user can create and edit planner items across all workbook lanes.
A user can filter by month, lane, campaign, owner, and status.
The system can pull supported HighLevel social and blog objects.
The system can push supported social posts and blog posts into HighLevel.
The system can sync email campaign visibility and status at minimum.
The system can show sync state and error state for each external item.
The product can support at least one future module without schema redesign.
